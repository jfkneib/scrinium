## 3 quater-a. DÉCISION 2026-10-26 : serveur Scrinium (PHP) + plugin « Partage » (voie A)
**Vision (l'utilisateur) :** chacun garde son Scrinium **personnel** ; seules les fiches qu'on choisit de **partager** passent par un **serveur Scrinium**. Scrinium n'est qu'un **client** : un plugin « Partage » (activé par chacun) se branche sur un serveur dont l'adresse est configurable. **Tout le monde** peut partager ses fiches (pas seulement l'administrateur) avec trois rôles : **propriétaire / écriture / lecture** (ex. Dédé en lecture-écriture, Alphonse en lecture seule). Le **serveur** fait respecter les droits (un Scrinium modifié ne contourne rien).
**Pourquoi pas Apache seul (WebDAV + htpasswd)** : les droits s'écrivent à la main dans la config → seul l'administrateur peut partager. **Pourquoi pas Nextcloud/Joplin** : applications complètes avec leur propre format ; Joplin Server : lecture seule documentée pour Joplin Cloud (Équipes), pas confirmée en auto-hébergé.
**Architecture :**
- **Serveur** : petit service **PHP** derrière Apache (HTTPS), **SQLite** (ou MariaDB), configurable (URL, chemin des données, compte administrateur). **Hébergement prévu : le Raspberry Pi `SERVEUR-TEST` (192.0.2.20)** : Apache 2.4 + PHP 8.4 + MariaDB 11.8, HTTPS déjà en place, redirection Freebox WAN 16443 → .61:443, sauvegarde quotidienne vers le XPS ; installable ailleurs (un dossier PHP + un fichier de configuration). Rien n'est modifié sur le Pi tant que l'utilisateur ne l'a pas demandé.
- **API** (JSON sur HTTPS) : connexion (jeton), lister les fiches partagées avec moi, lire, écrire **avec la version de départ** (refus si périmée → copie de conflit côté client), partager / retirer un droit (propriétaire seulement), historique.
- **Client** : plugin « Partage » : réglage du serveur et du compte, entrée « Partager… » sur une fiche, thème « Partagées » pour ce qui m'est partagé, copie locale (hors ligne) + synchronisation, conflits jamais écrasés en silence.
- **Sécurité** : HTTPS obligatoire, mots de passe hachés (`password_hash`), jetons à durée limitée, limitation des essais, sauvegardes, journal ; **le serveur peut lire les fiches NON verrouillées** (administrateur) → à dire clairement aux invités.
**Précisions du 2026-10-27 :**
- **Dépôt** : le serveur Scrinium va dans **le même dépôt git**, dossier `serveur/` (avec `public/index.php`, `src/`, `config.example.php`, `schema.*.sql`, `tests/`, `README.md`), contrat d'API dans `docs/api-partage.md`, tests client↔serveur (`php -S`), workflow `serveur.yml` ; la **vraie configuration n'est jamais dans git** (seulement `config.example.php`), les données sont **hors du dossier web** ; le serveur n'est **pas dans le `.deb`** (archive à part dans les releases, version d'API vérifiée par le client) ; même licence (GPL-3.0-or-later) ; développement sur la branche **`feat/partage`**, fusionnée dans `dev` quand elle est stable.
- **Base de données** : **SQLite par défaut** (un fichier ; extension `php8.4-sqlite3` installée sur le Pi `SERVEUR-TEST` le 2026-10-27, Apache rechargé) **puis MariaDB** en option (réglage `driver` du fichier de configuration), SQL portable (PDO), structures `schema.sqlite.sql` / `schema.mysql.sql`, tests sur les deux (MariaDB dans le workflow GitHub). L'XPS n'a pas l'extension SQLite pour PHP (seulement `pdo_mysql`) : les tests serveur tourneront surtout sur GitHub.
- **Plugin ou cœur** : la partie **visible** (réglage du serveur et du compte, « Partager… », thème « Partagées », synchronisation) est un **plugin « Partage »** livré avec Scrinium, désactivé par défaut ; mais l'**identifiant stable, la détection des changements, les conflits, les dépôts et (étape 3) le chiffrement pour plusieurs destinataires sont dans le cœur** (les plugins n'ont pas accès au stockage). Quelques fonctions s'ouvrent aux plugins (ajouts compatibles, API inchangée).
- **Installation et administration** : **un seul administrateur** (celui qui héberge). Il (1) dépose le dossier `serveur/` sur Apache, (2) copie `config.example.php` → `config.php` **hors du dossier web** (base `sqlite` ou `mysql`, adresse publique), (3) lance l'installation (`php install.php` ou page d'installation protégée) qui crée la base et le **compte administrateur**, (4) crée les comptes des autres (**inscription fermée par défaut**, invitation par lien à usage unique : la personne choisit son mot de passe). Rôles distincts : l'**administrateur** gère les comptes et le serveur ; chaque **propriétaire** gère les partages de ses propres fiches. Côté utilisateur : activer le plugin, saisir l'adresse du serveur et son compte.
**Étapes :**
1. ◐ **Cœur** (en cours, branche `feat/partage`, `docs/partage-coeur.md`) : ✔ identifiant stable par fiche (`Store.assurer_id`, `FicheVue.identifiant`, `ctx.assurer_identifiant`, copies détectées, 5 tests) · ✔ détection des changements et état de synchronisation (`core/synchro.py`, 9 tests) · ✔ conflits (`core/conflits.py` : table de décision, version locale mise de côté, distante reprise, rien de perdu, 7 tests) · ✔ dépôts, interface de transport, serveur de référence en mémoire et synchronisation de bout en bout (`core/depots.py`, `core/transport.py`, `core/synchroniser.py`, 26 tests) — **étape 1 terminée** (reste : suppressions et renommages simultanés, à l'étape 2)

**Idées de l'utilisateur (2026-10-26/29), à trancher à l'étape 4 :**
- **Ouvrir les droits avec une fiche** : le propriétaire décrit les droits dans une fiche (une ligne par personne : `dede : écriture`, `alphonse : lecture`) et Scrinium les applique au serveur ; ou, autre lecture de l'idée : une **fiche d'invitation** qui porte l'accès (voir ci-dessous). À préciser avec l'utilisateur.
- **Invitation par une fiche, avec un QR code** : la fiche contient l'adresse du serveur et un **jeton d'invitation à usage unique** (durée limitée, ex. 48 h, rôle et fiche ou thème visés, révocable par le propriétaire) sous forme de lien `scrinium://rejoindre?...` et de **QR code** (image jointe à la fiche). Elle s'envoie par le plugin Courriel existant ; le destinataire l'importe ou colle le lien. Deux cas à distinguer : (1) **inviter quelqu'un qui n'a pas de compte** (l'administrateur crée le compte via le jeton) ; (2) **partager avec un compte existant** (la fiche apparaît toute seule dans « Partagées », pas besoin de QR). Attention : une telle fiche est un **secret au porteur** (qui l'a peut rejoindre) → jeton à usage unique et expirant, jamais de mot de passe dedans, rappel à l'utilisateur de la traiter comme un mot de passe. QR : **génération seulement** au début (bibliothèque Python légère, ex. `segno`, optionnelle, installée avec accord) ; **la lecture** par caméra n'a de sens qu'avec un client mobile (plus tard) : sur ordinateur, on colle le lien.
